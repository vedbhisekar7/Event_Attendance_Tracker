# Architecture and explanation guide

## 1. Why this stack?

| Choice | Reason | Trade-off |
|---|---|---|
| Python + Flask | A few readable routes are enough for CRUD, file upload, and JSON APIs. Easy to test with Flask's test client. | A large multi-team system would benefit from more layers and deployment infrastructure. |
| SQLite through `sqlite3` | Durable, transactional storage in one file. No database server, Docker, account, or password needed. | Writes are serialized; not a substitute for a distributed/high-throughput database. |
| HTML, CSS, vanilla JavaScript | No build tools, bundler, CDN, or React knowledge required. Every button maps directly to a handler. | Explicit DOM rendering requires discipline about state and escaping. |
| Local font + SVG icons | The interface works offline after installation and has no runtime third-party asset requests. | Slightly larger source ZIP. |
| Native `<dialog>` | Built-in modal behavior, keyboard focus handling, and Escape support. | Requires a current browser. |

The goal is an understandable, well-tested local application, not a complicated production architecture.

## 2. Request flow

```text
Browser: HTML + CSS + app.js
   |
   | same-origin fetch() request
   v
Flask: app.py
   |---- validation.py: clean and validate data / inspect CSV
   |---- database.py: per-request connection
   v
SQLite: data/attendance.sqlite3
   |
   | result rows -> JSON
   v
app.js: render updated card, list, status and dashboard
```

The browser never changes an attendance count merely because a button was clicked. It waits for the server response, then refreshes database-derived statistics. A failed request displays an error rather than pretending it saved.

## 3. Files and responsibilities

- **`app.py`**: application factory, API endpoints, request limits, write-request guard, parameterized database queries, transactions, error responses, CSV download.
- **`database.py`**: a connection in Flask's request-local `g`, row dictionaries, foreign keys, busy timeout, initialization, connection cleanup.
- **`schema.sql`**: the source of truth for tables, uniqueness, status/timestamp consistency, and indexes.
- **`validation.py`**: rules shared by manual registration and CSV imports. The client is not trusted to validate correctly.
- **`seed.py`**: sample-only data, inserted when seeding is enabled and the new workspace has no events.
- **`templates/index.html`**: semantic page sections and native dialogs.
- **`static/js/app.js`**: one state object, hash-based page navigation, API wrapper, rendering, search, forms, CSV flow. Sections are labeled in comments.
- **`static/css/styles.css`**: color variables, layout, reusable components, responsive rules, and readability styles.

## 4. Data model

### Event

`id`, `name`, `event_date`, `venue`, `is_demo`, `created_at`.

### Participant (a registration for one event)

`id`, `event_id`, `name`, `college_id`, `email`, `phone`, `year`, `branch`, `present`, `checked_in_at`, `created_at`.

Relationship:

```text
events (1) -------- (many) participants
                    |
                    +-- UNIQUE(event_id, college_id)
                    +-- UNIQUE(event_id, email)
```

A separate global “student” table is intentionally not used. A registration is a snapshot of a student's details for one event. This makes importing, event isolation, and explanations straightforward. Editing a participant in one event does not change their details in another event.

The participant's numeric database ID is an internal record identifier. The **College ID** is a separate normalized field displayed to the organizer. The API always includes the event ID when fetching or changing a participant.

## 5. How attendance is saved

A new participant has:

```text
present = 0
checked_in_at = NULL
```

Check-in uses an explicit state-setting operation, not a toggle:

```sql
UPDATE participants
SET present = 1, checked_in_at = ?
WHERE id = ? AND event_id = ? AND present = 0;
```

- The timestamp is generated by the server in UTC.
- The update is committed to SQLite before success is returned.
- If a second request repeats the same check-in, the `present = 0` condition matches nothing. The first timestamp is kept and attendance is not counted twice.
- `changed: false` tells the browser the desired state was already set.
- Undo sets `present = 0, checked_in_at = NULL` after a UI confirmation.
- The database `CHECK` constraint requires a timestamp if and only if the participant is present.
- Editing a profile or importing extra attendance columns cannot bypass the dedicated attendance endpoint.

This is **idempotence**, not a claim of permanent audit history. Undo followed by a new check-in intentionally records a new timestamp. There is no record of earlier undo/check-in cycles.

Refresh and server restart do not reset the database. Browser storage is used only to remember the selected event.

## 6. How invalid / unknown College IDs are handled

1. **On registration:** trim and uppercase; require 2–32 allowed characters and a valid first character. Reject empty IDs, spaces, unsupported punctuation, and duplicates within that event.
2. **On search:** use a literal, parameterized partial search. A well-formed but unregistered ID produces no matches. Searching never creates a student.
3. **At the entrance:** the organizer chooses a matching registration, checks the physical card, and explicitly marks present. Multiple name matches are never auto-selected.
4. **On attendance write:** look up the record within the specified event. Missing or cross-event records return HTTP 404 and do not change attendance.
5. **Limits:** there is no official college registry integration, optical card scanning, QR verification, or proof that a physical card is genuine. The generic ID format can be changed in `validation.py` to match an institution's policy.

## 7. CSV imports are atomic

```text
Choose CSV
  -> decode UTF-8 (BOM accepted)
  -> normalize / check headers
  -> validate each nonblank row
  -> detect in-file and existing-event duplicates
  -> show preview and line-numbered errors
  -> user confirms
  -> repeat validation against the current database
  -> INSERT all rows inside one transaction
  -> commit, or roll back everything
```

A preview does not write. The file is not saved to disk. Upload and row limits constrain memory and processing. The UI lists at most the first 50 erroneous rows; the reported count still covers the entire file. Database unique constraints are the final protection if another organizer registers a duplicate between validation and insertion.

There is no partial import, implicit “skip duplicates,” silent overwrite, or attendance import. These are deliberate simplifications that make the outcome predictable.

## 8. Search, filtering, and client state

- The list endpoint supports a text query, attendance status, year, branch, sorting, and pagination.
- Search includes name, email, College ID, and digit-normalized phone numbers.
- SQL values use placeholders. Sort columns come from a fixed allowlist. SQL `LIKE` wildcards in the user's search are escaped and treated literally.
- For name and email, ordinary ASCII case-insensitive substring searching is enough for this assignment. Unicode text is stored, but SQLite's built-in ASCII-focused collation is a documented limitation.
- Search is debounced. Sequence numbers invalidate stale responses, so an older query or previous event cannot replace newer results.
- The event selection is a browser preference. All registration and attendance state stays in SQLite.
- Summary/list polling runs every 30 seconds while the tab is visible and no dialog is open; local successful changes refresh immediately. This is polling, not WebSockets.

## 9. API map

All modifying requests need the header `X-Requested-With: Gather`. This is a same-origin write-request guard, **not authentication**.

| Method | URL | Purpose |
|---|---|---|
| GET | `/api/health` | Test database connection |
| GET / POST | `/api/events` | List / create events |
| GET | `/api/events/<event_id>/summary` | Event metrics, breakdowns, recent arrivals |
| GET / POST | `/api/events/<event_id>/participants` | Search / register |
| GET / PATCH / DELETE | `/api/events/<event_id>/participants/<id>` | Fetch / edit / delete |
| PUT | `/api/events/<event_id>/participants/<id>/attendance` | Set `{"present": true}` or `{"present": false}` |
| POST | `/api/events/<event_id>/import/preview` | Validate multipart file field `file` |
| POST | `/api/events/<event_id>/import` | Validate and atomically import multipart file field `file` |
| GET | `/api/events/<event_id>/export` | Export all rows matching current filters |
| GET | `/api/template.csv` | Download a valid sample template |

List query parameters: `q`, `status` (`all`, `present`, `absent`), `year`, `branch`, `sort` (`name`, `newest`, `checkin`), `page`, `page_size` (1–100). The reserved filter value `__unspecified__` matches a blank year/branch.

Responses use useful status codes: 201 created, 400 validation failure, 403 missing write guard, 404 unknown event/participant, 409 duplicate registration, 413 oversized upload, 503 database busy/unavailable.

Example check-in from a shell (replace event and participant IDs with real ones):

```bash
curl -X PUT http://localhost:8000/api/events/1/participants/3/attendance \
  -H 'Content-Type: application/json' \
  -H 'X-Requested-With: Gather' \
  -d '{"present": true}'
```

## 10. Reliability and security boundaries

Implemented:

- Parameterized SQL and hardcoded sort options.
- Server validation for manual inputs and CSV rows.
- Database uniqueness and status consistency constraints.
- Transactional imports and idempotent check-in.
- Per-request SQLite connections, WAL mode, and a 10-second busy timeout.
- Escaped user text in DOM templates; no user-provided HTML is executed.
- Spreadsheet formula escaping in CSV exports.
- No permissive CORS; custom-header guard on writes; same-origin frontend requests.
- Basic content security and no-sniff response headers. API responses are not cached.
- Friendly failures; server logs contain diagnostics. Debug mode is off.

Not implemented: user authentication, authorization, tamper-proof audit records, rate limiting, cloud replication, long-term student data governance, event deletion, a production WSGI deployment, or persistent hosting. Do not present the request header as a security boundary against someone who can access the server. It is not a password or a session token.

## 11. Changes you should be able to make

1. **Change the theme:** edit `:root` colors and the stat-card colors in `styles.css`.
2. **Restrict College IDs:** update `COLLEGE_ID_RE` and its validation message; adjust tests and the README.
3. **Add an optional field:** update `schema.sql`, `validate_participant`, CSV headers, insert/update statements, the form, and UI detail rendering. Existing databases require a deliberate migration—`CREATE TABLE IF NOT EXISTS` alone does not add a column.
4. **Change demo content:** edit `seed.py`; use a separate empty database to see new seed values without deleting attendance you need.
5. **Change refresh frequency:** update `setInterval` and its visible “30s refresh” label together.
6. **Add organizer accounts:** introduce real authentication/authorization and protect all routes before using real registrations on an accessible network.

For a presentation, explain the happy path, show one invalid CSV, show an unknown College ID, and demonstrate refresh persistence. Be honest about the limits above and any AI assistance used, as required by your assessment policy.
